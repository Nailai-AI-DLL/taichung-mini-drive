## 0. 一頁摘要

- **做什麼**:瀏覽器上的 3D 開車遊戲。玩家用鍵盤開一台 Q 版 MINI Cooper F55 五門(60 週年紀念版,黑車身白車頂),在依真實路網生成的台中市區裡自由兜風,路名與主要地標盡量接近真實。
- **怎麼做**:three.js + TypeScript + Vite;物理用 Rapier;地圖用 **OpenStreetMap 資料離線轉檔**生成路網與建築;MINI 與地標用 Blender 腳本建模(`docs/decisions/0007-m0-feedback.md` 第 5 項)。
- **關鍵轉向**:需求寫的是「參考 Google Maps 的資料」,但 Google Maps 條款**不允許**擷取或描繪它的資料拿來建自己的地圖(詳見 §4.2)。因此改用 OSM(加上臺中市政府開放資料)當資料來源,Google 任何產品都不進入製作流程;地標外觀改用自拍或開放授權照片當參考。Cooper 已同意(Q1)。
- **MVP**:範圍 A(台中車站 ↔ 七期,約 6.6 × 5.0 km),1:1 比例,**純自由兜風**;輕快好甩的街機手感,無 Boost;配色接近真實、低彩度淡雅(2026-10-12 由粉彩奶油改定,§10.1);Lo-fi 背景音樂。
- **使用情境**:只在 Cooper 自己電腦上玩,最多對外分享錄影影片(影片的授權標示義務見 §9)。
- **拍板紀錄**:見 §10。

## 2. 產品定位與核心體驗

**一句話**:「開著 Q 版 MINI,在一個很可愛但你認得出來的台中裡亂逛。」

三根支柱(後續所有取捨以此為準):

1. **認得出來的台中** — 路名對、地標在對的位置、長得像。台中人開過台灣大道接文心路要有「啊,就是這裡」的感覺。
2. **開起來爽** — 街機手感(arcade):起步快、好甩尾、撞到不會卡死、隨時一鍵回到路上。不追求擬真。
3. **可愛極簡** — 純色、圓角、Q 版比例、小小的彈跳動畫與音效回饋。畫面乾淨,資訊少。

**不做的事(MVP 階段)**:擬真物理、車損、多人連線、車輛改裝、全台中市範圍、手機觸控。

### 3.3 手感取向(Q7:輕快好甩好開)

以下是 Claude 對「輕快好甩好開」的初步詮釋,M0 試開時由 Cooper 確認:

- 起步快、轉向反應靈敏,低速也容易甩尾;放開手煞車後自動回正、不易打滑失控。
- 高速時轉向自動收斂,避免一碰就失控;撞牆後快速恢復,不卡住。
- 具體數值(0–100 km/h 時間、煞車距離、迴轉半徑)在 M0 用調參面板做出初版,Cooper 試開核定後寫入自動測試。

### 3.4 鏡頭

- 預設:彈簧臂追尾鏡頭,略帶延遲跟隨;速度越快 FOV 越寬(速度感)。
- 甩尾時鏡頭略往外側偏,保持看得到前方。
- 高空俯視視角:類 isometric 斜俯視,方便認路。

### 3.5 HUD 與 UI

- **路名牌**(畫面上方中央):駛入新道路時滑入,樣式仿台灣藍底白字路名牌(例:「臺灣大道二段」),Q 版圓角化。這是「認得出台中」最直接的呈現。
- **小地圖**(右下):道路線條 + 主要路名 + 地標圖示,北朝上/車頭朝上可切。
- **速度表**(左下):圓形可愛儀表,km/h。
- **地標提示**:接近地標 150 m 內浮出名稱與距離。
- 字型建議:jf open 粉圓(圓體,SIL OFL 1.1,可隨遊戲散布、含商業)。須附 OFL 全文;若為了縮小檔案而只取用到的字(子集化),就不能再沿用原字型名稱,必須改名。

### 3.6 世界規則

- 建築物為實心碰撞;路燈、行道樹、垃圾桶等小物件**可被撞飛**(可愛的彈飛動畫),不造成車損。
- 地圖邊界:柔性邊界(雲朵或圍欄),靠近時提示「再往外就是未開放區域」並輕推回來。
- 交通車流、紅綠燈、行人:MVP 不做(§10 Q6)。
- 存檔:MVP 只存設定(音量、畫質)於瀏覽器 localStorage。
- 開場畫面與選單的「關於」頁顯示 OSM 與政府資料來源標示(錄影時可錄進去,見 §9)。

## 4. 地圖與資料策略

### 4.1 範圍與比例

| 方案 | 範圍 | 面積 | 包含的代表地標 | 評估 |
|---|---|---|---|---|
| **A 核心(已定 MVP)** | 台中車站 ↔ 七期,台灣大道走廊 | 約 6.6 × 5.0 km ≈ 33 km² | 台中車站、台中公園、宮原眼科、國美館、科博館、草悟道、勤美、歌劇院、市政府、新光三越/大遠百、秋紅谷 | 地標密度最高,資料量可控 |
| B 擴大 | A + 逢甲、東海、洲際棒球場 | 約 11.2 × 7.8 km ≈ 87 km² | A + 逢甲夜市、路思義教堂、洲際棒球場 | 東海一帶在大肚山台地,需要地形高低差 |
| C 全台中市 | 全市 | 約 2,215 km² | 含高美濕地、台中港等 | 不建議:資料量與效能成本高,地標稀疏、空曠段多 |

**OSM 實查數字**(快照 2026-10-11,詳見 `docs/research/osm-taichung-feasibility.md`):

| 指標 | 範圍 A | 範圍 B |
|---|---|---|
| 可行駛道路 | 844.9 km / 6,055 段 | 1,832.3 km / 11,649 段 |
| 路名覆蓋率(依長度;不含 service 道路) | 97.9% | 95.8% |
| 建築數 | 12,518 | 20,121 |
| 有高度或樓層數 | 60.0% | 52.1% |
| 有實際高度(height 標籤) | 1.3% | 0.9% |
| 有車道數(lanes) | 約 13% | 約 13% |

結論:**路網與路名足夠**(幹道路名約 100%);**建築高度主要靠樓層數推估**,約四成建築連樓層數都沒有,需預設規則(§10 Q12);**路寬主要靠預設值**。

**比例 1:1(Q3 已定)**。理由:(1) 需求要求「接近實際」,1:1 才能讓路口間距、街廓大小有真實感;(2) 壓縮比例會讓道路寬度與建築尺度一起變形,反而不像;(3) 實際距離不長——台中車站到歌劇院約 5.5 km,遊戲內時速 100 km/h 約 3 分多鐘,自由兜風剛好。速度感用 FOV、動態模糊感線條、音效補足,不靠縮地。

| 臺中市 20m DTM 數值地形 | 範圍 B 的地形 | 可用,開放授權 |

### 4.3 地圖生成管線(離線,建置時跑一次)

```
Overpass 下載(data/osm/raw/*.json)
  → 投影:經緯度 → TWD97 TM2(EPSG:3826)公尺座標 → 平移到原點(地圖中心)
  → 套用人工覆寫(data/overrides/*.json)
  → 道路:依道路等級/車道數決定寬度 → 每條路生成帶狀多邊形 → 以 Clipper 聯集(路口自然合併)→ earcut 三角化
  → 標線:中線/車道線/斑馬線(路口附近自動省略)
  → 建築:輪廓擠出,高度 = height 標籤 → 樓層數 × 3.2 m → 依建築類型與面積推估(Q12);以 OSM id 為種子決定配色與屋頂小物
  → 地標:在對應位置挖掉 OSM 原建築,改放手工模型
  → 道具:行道樹、路燈、機車排、招牌 → 以 InstancedMesh 佈置點位
  → 分塊:250 m × 250 m 一塊,輸出 GLB(meshopt 壓縮)+ 路名索引 JSON
  → public/map/
```

道路寬度預設(有 `lanes` 標籤時改用「車道數 × 3.3 m + 路肩」):

| OSM 等級 | 預設寬度 | 台中例子 |
|---|---|---|
| trunk | 24 m | 快官霧峰線(範圍 A 內唯一的 trunk) |
| primary | 24 m(臺灣大道以 overrides 個別設定) | 臺灣大道、文心路、五權路 |
| secondary | 18 m | 公益路、英才路 |
| tertiary | 12 m | |
| residential / unclassified | 7 m | 巷弄 |
| service | 4.5 m | |

上表為初始值(未經實測,not_stated 實際路寬)。M0 時依 Q13 的決定,用臺中市政府「道路寬度」開放資料校正(對應到 OSM 道路),結果寫入 overrides;**不使用 Google 街景量測**(Google 條款明文禁止從街景影像產生資料)。

管線需處理的 OSM 特性(實查發現):
- 主幹道雙向常分成兩條線(如臺灣大道),生成路面時要合併中間分隔帶。
- 捷運綠線、台鐵在 OSM 的高架標記本次未查(not_stated);M0 時確認,若為高架需做高架結構並避免與路面碰撞衝突。
- 臺灣大道一律寫「臺」(寫成「台灣大道」的是 0 筆);台中路、中台路等本名用「台」的路照原名。遊戲內一律沿用 OSM 原文。
- OSM 的英文路名(name:en)有錯誤,不能直接顯示,需抽查後再決定。

### 4.4 路名系統

- 建置時把每段道路的中心線、路名(含「段」)、英文名存成索引。
- 執行時用空間索引查車輛位置附近 15 m 內、方向一致的路段 → 決定「目前道路」;0.5 秒防抖,避免在路口閃爍。
- 路口放 Q 版路名牌模型(藍底白字),小地圖顯示主要路名。

### 4.5 地形

- 範圍 A 推論大致平坦(位於台中盆地;範圍 A 內的海拔本次未實測,not_stated)→ MVP 用平面,M0 時以 20m DTM 確認。
- 實查:路思義教堂比臺中車站高約 100 m(衛星地形 180 m 對 78 m);範圍 B 內已知最高水準點 227.38 m → 範圍 B 必須有地形。
- 擴大到東海(大肚山台地)時,再引入數值地形模型讓道路貼地(M4)。

## 5. 美術方向

### 5.1 整體風格

- **低多邊形 + 純色**:不用貼圖,全部用頂點色或少量純色材質 → 檔案小、風格統一、易於程式化生成。
- **圓角**:建築邊角、車體、路牌都有小倒角。
- **柔和光影**:一盞方向光(暖色)+ 半球環境光(天藍/草綠),陰影只在玩家車附近計算。
- **遠景**:淡淡的霧與漸層天空,同時遮住分塊載入邊界。

### 5.2 色票(Q9 原採方案甲;2026-10-12 看過 M0 樣張後改方向,見下)

| 人行道 | `#F3E9D2` 奶油 | `#E9E3D5` |
| 草地/公園 | `#B8E0C2` 薄荷 | `#7BC96F` 草綠 |
| 住宅建築 | `#F6D6C3` 蜜桃 / `#FBE8A6` 奶黃 | `#FFB4A2` / `#FFD166` |

### 5.3 MINI Cooper 造型

- 車型(Q10):**MINI Cooper F55 五門,60 週年紀念版,黑色車身 + 白色車頂**。
- Q 版比例(建議,M1 出模型時請 Cooper 確認):五門車身較長,為保留「五門」辨識度,車身只縮短約 5–10%(仍看得到前後兩扇側門),車輪放大約 20%,車頂略圓。
- 可辨識元素:圓形大頭燈、白色車頂、五門車身比例、大輪拱。
- 60 週年紀念版的專屬細節(引擎蓋條紋樣式、徽章位置、輪圈款式、尾燈造型、後視鏡外殼顏色):not_stated,M1 前查證。**建議以 Cooper 自己拍的實車照片當參考**(若方便提供),這也最符合 Q1 的參考來源原則。
- 只做這一款(黑車身白車頂),不開放換色(Cooper 2026-10-12 補答)。
- 小動畫:加速車身後仰、煞車前傾、甩尾時輪胎冒小白煙、喇叭時車燈眨一下。
- 製作方式:M0 為程式碼組合基本幾何體(0002);M1 起改用 Blender 腳本建模(0007 第 5 項,已決定),同樣可版控、可重做。

### 5.6 音效與音樂

- 引擎聲:以 Web Audio 合成,音高隨轉速變化,音色偏可愛(像玩具車)。
- 其他:喇叭、甩尾、撞飛小物件的「啵」。
- 背景音樂(Q11):**Lo-fi**。來源限 CC0 或自製,授權逐一登記在 `docs/assets-licenses.md`(M1 建立)。若之後要分享錄影影片,音樂授權必須允許用在公開影片。

## 6. 技術架構

### 6.1 技術選型(細節與放棄方案見 `docs/decisions/0002-tech-stack.md`)

| 層 | 選擇 | 理由 |
|---|---|---|
| 語言/建置 | TypeScript + Vite | 型別安全、開發伺服器快 |
| 渲染 | three.js(WebGLRenderer) | 需求指定;WebGPU 視之後成熟度再評估 |
| 物理 | Rapier(`@dimforge/rapier3d-compat`) | WASM 效能好、內建射線懸吊車輛控制器、可在 Node 跑測試 |
| 地圖建置 | Node 腳本:proj4、clipper2、earcut、gltf-transform | 離線處理,執行期不需要地圖運算 |
| 空間索引 | flatbush | 路名查詢、最近道路查詢 |
| 除錯 | lil-gui、stats.js | 手感參數即時調整 |
| 測試 | Vitest(單元)、Playwright(冒煙/效能) | |

### 6.2 執行期模組

```
src/
  core/       遊戲迴圈(物理固定 60 Hz,渲染跟隨螢幕)、事件匯流排、設定
  input/      鍵盤對應(可重綁)
  vehicle/    車輛控制器(街機輔助:轉向隨速衰減、甩尾、防翻、自動扶正)
  camera/     追尾/俯視鏡頭
  world/      分塊串流載入/卸載、霧、光影、道具 instancing、碰撞體管理
  landmarks/  每個地標一個建模函式
  map/        路名索引、最近道路、小地圖資料
  ui/         HUD、路名牌、小地圖、選單
  audio/      引擎合成、音效、音樂
  modes/      自由兜風(打卡、計時等模式於 M4 評估後再加)
  debug/      調參面板、碰撞體可視化、座標顯示
tools/
  map-build/  地圖建置管線(§4.3)
  research/   資料調查腳本
data/
  osm/raw/    OSM 原始資料(不打包進遊戲)
  overrides/  人工覆寫(路名、高度、地標位置)
public/map/   建置產物(GLB 分塊 + JSON 索引)
```

### 6.3 效能預算(提案)

| 指標 | 目標 |
|---|---|
| 幀率 | **Cooper 的 M1 Pro**(2026-10-12 改定),1920×1080,平均 ≥ 58 fps(目標 60 fps);DPR 1 與 DPR 2 都要測 |
| Draw calls | 每幀 < 300(分塊合併網格 + instancing) |
| 首次進入遊戲 | < 10 秒(以 Chrome DevTools 節流 50 Mbps 量測) |
| 範圍 A 地圖資料總量 | < 30 MB(壓縮後) |
| 同時載入分塊 | 車輛周圍半徑約 750 m,其餘卸載 |

## 8. 驗證與測試策略

| 對象 | 方法 |
|---|---|
| 座標投影 | 單元測試:以獨立實作(`tools/research/twd97_to_wgs84.py`)或官方控制點為參考,已知點經緯度 → TWD97 公尺座標誤差 < 0.01 m |
| 路名正確性 | 固定測試點表(座標 → 預期路名),自動比對;另由 Cooper 依實地經驗抽查 |
| 地標位置 | 自動測試:模型中心與 OSM/參考座標誤差 < 10 m |
| 道路連通 | 建置時檢查:可行駛路網的最大連通分量占比、孤立路段清單 |
| 車輛手感 | 在 Node 裡用固定時間步跑 Rapier:0–100 km/h 時間、100–0 煞車距離、最小迴轉半徑,斷言落在核定範圍 |
| 執行穩定性 | Playwright 冒煙測試:載入、無 console error、自動駕駛 10 秒速度 > 0 |
| 效能 | Playwright 跑固定路線,取樣 fps 與 draw calls,輸出報告 |
| 規格文件 | 由全新 context agent 做反向重述,比對需求 |

本專案不涉及機率、賠付、金額,該類驗證規則不適用。

## 9. 風險與對策

| 風險 | 影響 | 對策 |
|---|---|---|
| Google Maps 資料不可直接使用 | 原需求「參考 Google Maps 資料」需調整 | 改用 OSM + 政府開放資料(Q1 已同意) |
| **對外分享錄影影片** | 遊戲畫面屬 ODbL 的 Produced Work,影片公開即為公開使用 | (1) 影片內(開場或片尾)或影片說明欄放「© OpenStreetMap contributors」與臺中市政府資料來源標示;遊戲開場畫面已內建,錄進去即可。(2) 因 Q13 混用 OSM 與政府路寬,依 ODbL §4.4(c)/§4.6,須主動表明可提供轉換方法:影片說明欄加一句「可索取地圖衍生資料或轉換方法」,有人索取時提供 `tools/map-build/` 腳本與 `data/overrides/`。(3) 背景音樂須允許用在公開影片。以上為依研究報告的推論,非法律意見 |
| OSM 資料缺漏(路名、建築高度) | 部分路段沒路名、建築高度不準 | 依類型與面積的預設高度(§10 Q12);人工覆寫檔。臺中市建物圖是否有樓層或高度欄位尚未確認(not_stated),且拿它補 OSM 會觸發授權共享義務 |
| MINI 商標與車型外觀 | 遊戲本體不散布;影片中可看到車型 | 照實車做;架構保留「去除 MINI 字樣與 logo」的開關,日後若改變使用情境可切換(Q4、Q14) |
| 商場名稱/logo | 影片中可看到 | 建築外觀做形體即可,不放 logo;名稱只用於地標提示文字 |
| 建築數量多導致效能不足 | 卡頓 | 分塊合併、instancing、遠處簡化、霧遮蔽 |
| 手感屬主觀 | 反覆調整 | 參數全部外部化 + 調參面板,Cooper 試駕後核定數值範圍並寫入測試 |
| 範圍膨脹 | 拖延 | MVP 鎖範圍 A;M4 項目逐項由 Cooper 決定 |

授權細節(Google 條款、ODbL 義務、商標、著作權法第 58 條)見 `docs/research/data-licensing.md`。以上不構成法律意見。
