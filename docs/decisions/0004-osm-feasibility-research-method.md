# 決策紀錄:OSM 台中資料可行性調查(2026-10-11/12)

範圍:docs/research/osm-taichung-feasibility.md 的研究方法。以下都是純技術、可逆的選擇,由執行 agent 自行決定;商業與品味相關的事項(層高預設、地標清單取捨)留給 Cooper。

| 決策 | 理由 | 放棄的方案 |
|---|---|---|
| 只對區域 B 抓一次資料,區域 A 由腳本裁切(Liang-Barsky + haversine) | 節省 Overpass 配額(上限 12 次);A 完全包含在 B 內 | A、B 各抓一次:會多用請求數,而且仍需處理邊界 way 被重複計算的問題 |
| 道路長度用「bbox 內裁切後長度」,way 數用「裁切後長度 > 0」 | 避免跨界的長 way 把整條長度都算進區域 | 用整條 way 長度:會高估 |
| 建物、公園以 Overpass center 是否落在 bbox 內決定歸屬 | q02 只抓 tags+center,資料量小 | 抓建物完整幾何:檔案太大,這個統計用不到 |
| 查詢參數降為 [timeout:90][maxsize:128MB] | 用 180 秒與預設 maxsize 時,dispatcher 回 504 | 一直重試原參數 |
| 地標與 OSM 元素的對應人工寫死在 osm_landmarks.py | 名稱比對有大量雜訊(公車站、停車場、同名建案) | 純自動名稱比對:誤配率高 |
| 宮原眼科輪廓 = 包含 POI node 的無名建物(標為推論) | OSM 沒有具名輪廓 | 寫 not_stated:會失去可用的近似輪廓 |
| 最高建物用公開資料(維基)判定,OSM 只用來定位 | OSM height 覆蓋率不到 1% | 只看 OSM height 排名 |
| 海拔:OSM 測量點 + OpenTopoData SRTM30m 互相驗證 | 兩個獨立來源;用水準點量化 SRTM 的誤差 | 只引用文字資料:沒有精確數字 |
| 外觀描述以中文維基為主,不足時用英文維基、新聞或官方影視頁補充;單一部落格說法不採用 | 可查證性 | 引用部落格:可信度低 |
