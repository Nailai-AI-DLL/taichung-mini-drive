# 0012 地圖資料格式 v2 與分塊生成

- 日期:2026-10-24
- 狀態:**已決定**(純技術;Claude 依 CLAUDE.md「純技術、可逆、單一專案」原則自行決定)
- 依據:`decisions/0009` T1、T2;`milestones/M1-progress.md` 確認點 1「範圍 A 資料量」風險(舊格式估計約 50 MB)

## 1. 問題

M0 的格式在建置時就把建築擠出成網格，位置、法向量、顏色、索引全部存進 map.bin。範圍 A 約 12,500 棟建築，估計約 50 MB,超出 30 MB 預算。而且整張地圖一次建成單一網格，不能只畫車子附近。

## 2. 決定

| 項目 | 決定 |
|---|---|
| 傳輸內容 | 只傳 2D 描述:道路折線 + 路面寬 + 旗標;建築外框(含內環)+ 高度 + 顏色索引;綠地/水面多邊形;水道折線 |
| 檔案格式 | **單一 JSON**(`public/map/<area>/world.json`),座標存成 0.1 m 整數。整份在開場一次載入 |
| 網格生成 | 執行期在瀏覽器生成。生成程式從 `tools/map-build/lib` 搬到 `src/world/gen/`,建置端和執行端共用 |
| 分塊 | 250 m × 250 m 一格。開場把所有物件分到格子:建築依中心點，道路與面依裁切。只生成車子周圍半徑 R 內的格子,R 比霧的終點 720 m 略大;超過 R + 遲滯距離就卸載 |
| 每格的網格 | 地面類(道路 + 人行道 + 綠地 + 水)合併成 1 個網格，建築 1 個網格 → 每格 2 個 draw call |
| 碰撞 | 每格一個建築三角網格碰撞體，跟著格子建立與移除 |
| 生成節奏 | 開場先同步生成出生點附近的格子;之後每幀最多花 4 ms,由近到遠生成。實測若超出單幀預算，再改用 Web Worker |
| 路寬 | 依 `decisions/0011`:政府路寬扣掉兩側人行道;分隔幹道依 way 數平分 |

## 3. 放棄的方案

| 方案 | 放棄理由 |
|---|---|
| 分塊二進位檔(每格一個 .bin)+ 16 位元量化 | 2D 描述本身就小(估計數 MB),不需要分檔串流;二進位格式要多寫編解碼程式和測試，除錯也比較難。之後超出預算再改 |
| 建置時就生成網格，存成分塊 GLB(0006 第 1 項原本要評估的方向) | 資料量仍然是網格級，和 2D 描述差一個數量級 |
| 一次生成整張地圖 | 12,500 棟建築的網格和碰撞體一次建好，記憶體和開場時間都高;而且全部畫出來的 draw call 多 |
| 用 InstancedMesh 方塊畫建築(slop-newyork 的做法) | 台中建築外框不規則;圓角是可愛化的特色 |

## 4. 驗證方式

- 單元測試:2D 描述經 client 端生成的網格，和直接生成的結果一致(頂點數、包圍盒);分塊邊界不遺漏建築;卸載後碰撞體數歸零。
- 資料量:量 world.json 原始大小與 gzip 後大小，對照 30 MB 預算。
- 效能:Chrome 實跑(M1 Pro 內建螢幕，DPR 1 與 2),開全區一圈，量平均 fps、最長單幀、draw calls、生成耗時。

## 5. 實作結果(2026-10-24)

- world.json 2,898 KB,gzip 732 KB(預算 30 MB)。
- Chrome(M1 Pro 內建螢幕)DPR 1、DPR 2 都是平均 120 fps;以 72 m/s(2 倍極速)穿越 1.4 km,沒有超過 33 ms 的卡頓幀;單格生成最長 9.8 ms。
- 結論:單一 JSON 加上主執行緒分時生成就足夠,**不做 Web Worker**。如果之後地標或道具讓單格生成超過 16 ms,再改用 Worker。
- 詳細數據見 `milestones/M1-progress.md`「架構階段 第 2 段」。
