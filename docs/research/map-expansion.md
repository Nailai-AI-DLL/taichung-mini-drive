# 地圖擴展評估(以 2026-11-17 的規模推估)

## 現況(實測)
- 範圍 A:6.6 × 5.0 km = 33 km²(台中車站 ↔ 七期)。
- `world.json`:21.2 MB(gzip 5.2 MB);其中建築 19.8 MB(119,670 棟,約 170 bytes / 棟)、街道細節 1.7 MB、傢俱 2.2 MB、道路 1.5 MB。
- 執行時：開場一次載入整個 world.json、解成 560 格(每格 250 m);畫面只生成車子周圍 800 m 內的格子(串流)。
  - 載入 1.1–2.1 秒(e2e);JS heap 約 194 MB(frame-spikes);單格生成最長 13–17 ms;平均 60 fps。
- 建置 `npm run map:build:range-a` 約 50 秒。

## 候選範圍(建物圖實際筆數;其餘為線性推估)
| 範圍 | 大小 | 建物圖筆數 | world.json 推估 | gzip 推估 | 載入推估 | 記憶體推估 |
|---|---|---|---|---|---|---|
| A 現在 | 6.6 × 5.0 km、33 km² | 122,092 | 21 MB | 5 MB | 1–2 秒 | ~0.2 GB |
| B 加北屯、南區、大里北 | 10.7 × 9.4 km、100 km² | 298,224 | ~52 MB | ~13 MB | ~4 秒 | ~0.5 GB |
| C 市區 8 區 + 西屯南屯北屯 | 15.8 × 13.3 km、209 km² | 503,006 | ~88 MB | ~22 MB | ~7 秒 | ~0.8 GB |
| D 全市 | 101.6 × 50.9 km(多為山區) | 1,263,194 | ~220 MB | ~55 MB | 不可行 | > 2 GB |
- 推估方式：依建物筆數等比例放大(建築佔檔案 93%);載入、記憶體依現況線性放大。**都是推論，沒有實測。**

## 瓶頸
1. **開場一次載入整張地圖**:檔案、解析時間、記憶體都和面積成正比。B 還算可以;C 開場要等好幾秒、記憶體接近 1 GB(手機、低階筆電可能不行)。
2. 每幀的效能(串流)和面積無關：只看車子周圍，範圍變大不會變卡。
3. 建置時間線性：C 約 5 分鐘，可以接受。
4. 資料：市政府建物圖、行道樹、道路圖、路寬都涵蓋全市;OSM 可以再抓。地標模型、知名地點、接送地點目前只在 A。

## 結論
- **不改架構**:可以擴到約 **B(100 km²,現在的 3 倍)**。
- **要到 C 以上**:先把 world.json 切成分區小檔、開車到附近才下載(串流載入),記憶體和開場時間就不再隨面積變大。工作量中等(建置輸出分檔、執行端按需下載、測試)。做完後 C 可行;全市大多是山區，價值低。
- 建議先擴到 B 實測，再決定要不要做分區載入。

## 追加(2026-11-17):全台中(和平區除外)+ 分區載入 + 伺服器
Cooper:「除了和平區之外的台中區域都包含進去。一開始載入只先以某幾區為主(例如西屯區、北區、西區、南屯區),其他區域放在背景陸續載入。」「這些地圖資料是不是放在伺服器上用來載入會更適合？」

### 規模(推估)
- 臺中市 29 區扣掉和平區：約 1,180 km²(和平區佔全市約一半，多為山地)。建物圖全市 126 萬筆，和平區很少 → 約 124 萬棟。
- 地圖資料總量約 210 MB(gzip 約 50 MB),是現在的 10 倍。

### 「先載幾區、其他背景陸續載入」
- **方向可行，但「背景把全部載完」不行**:全部進記憶體約 2 GB 以上，瀏覽器分頁會被系統關掉或很卡。
- 建議改成「依距離載入、遠的丟掉」:地圖切成很多小格檔(例：每 1 km 一檔),開場只下載出生點周圍(西屯、北區、西區、南屯這幾區可以先下載)、開車時預先下載前方、離太遠的從記憶體移除。記憶體固定在現在的量級，地圖再大都一樣。
- 「先載幾區」可以當成「開場預先下載的範圍」:玩家一開始在這幾區，等它們下載完就能開;其他區域開到附近才下載(或閒置時慢慢預先下載，但只存在瀏覽器快取、不進記憶體)。

### 跟著要處理的事
1. 地圖檔改成分格檔 + 執行端按需下載、卸載(核心，工作量中到大)。
2. 全域的輕量資料另外一份：大地圖 / 小地圖底圖(只有道路、水面，簡化過)、接送地點、地標清單。
3. 其他車輛、接送任務現在用「整張地圖的道路」:要改成只用已載入的格子。
4. 地形：目前地圖是平的(0010 A1)。台中盆地內 OK,但全台中包含大肚山台地、東邊丘陵(新社、東勢),平的會很怪 → 要另外決定(做地形高低是大工程)。
5. 座標精度：遊戲用一個原點，全台中東西約 50 km;離原點 25 km 外，GPU 的精度約 2–4 mm,一般看不出來，但物理和陰影可能抖動 → 可能要「原點跟著玩家移動」。
6. OSM 要分區下載(一次抓全台中太大);市政府資料已涵蓋全市。
7. 地標、知名地點、接送地點目前只在現在的範圍。
8. 建置時間：全部重建約 10–20 分鐘;要改成只重建有變的格子。

### 伺服器
- **要放在網路上，但不需要「會運算的伺服器」**:分格檔是固定的靜態檔，放在任何靜態網站 / 檔案空間都可以(像地圖 App 的圖磚)。
- **不建議繼續把地圖檔 commit 進 git**:world.json 已經進版控 18 次，`.git` 已 274 MB;全台中每重建一次就多 ~50 MB,repo 會很快變肥。
- 選項：
  | 方式 | 費用 | 優點 | 缺點 |
  |---|---|---|---|
  | GitHub Pages,地圖檔放另一個分支、每次整個覆蓋 | 免費 | 不用新帳號，網址不變 | Pages 網站上限 1 GB、每月流量 100 GB(軟限制);要改部署流程 |
  | Cloudflare R2(檔案空間)+ 現在的 Pages | 免費額度 10 GB 儲存、下載流量免費 | 容量夠、流量不收錢 | 要開 Cloudflare 帳號(Cooper 決定) |
  | GitHub Releases 附檔 | 免費 | 不進 git 歷史 | 不適合幾千個小檔 |
- 建議：先用「GitHub Pages + 地圖檔另一個分支」(不用新帳號),流量或容量不夠再搬 R2。

### 建議的順序
1. 分格檔 + 按需下載 / 卸載(先用現在的範圍 A 做，確認效能)。
2. 地圖檔移出 main 分支(順便解決 repo 變肥)。
3. 擴到盆地內的區(西屯、南屯、北屯、北、西、中、東、南、大里、太平、烏日…),地形仍是平的。
4. 再決定要不要做地形，才擴到海線、山線。
